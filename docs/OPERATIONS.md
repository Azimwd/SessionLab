# Администрирование и эксплуатация

## Мастер кампании

Права привязаны к Membership кампании, а не к глобальному staff. Создатель кампании автоматически dm. Другой мастер назначается через «Участники → Сменить роль». Владелец сохраняет роль, его нельзя отключить этой операцией. Staff в Django Admin не получает доступ к чужой кампании через REST API автоматически.

### Сессии

Создайте planned-сессию, укажите дату и при необходимости overrides. Нажмите «Начать», чтобы открыть выдачу эффектов и квестов. Одновременно активна одна сессия. Завершение необратимо через интерфейс: эффекты/квесты истекают, ожидающие согласования закрываются. Открытые карточные раунды блокируют завершение, чтобы не оставить замороженную ставку.

Настройки сессии задаются JSON, например:

```json
{"effect_limit":1,"quest_limit":2,"casino_enabled":true}
```

Отсутствующие поля берутся из кампании. Не нужно копировать весь объект настроек кампании в каждую сессию.

### Эффекты и квесты

Общую библиотеку мастера не меняют: кнопка копирования создаёт независимый контент кампании. Его можно редактировать, отключать и архивировать. Все выданные результаты хранят снимок текста и правил; изменение определения не меняет прошлое. «Архивировать» не удаляет исторические связи.

Сложные поля редактируются рабочим JSON-редактором. Нужны корректные типы: active/homebrew/requires_approval — boolean, weight/use_limit/reward — целые числа, parameters — объект. Указание `secret` хранит заметку только для мастера; она не возвращается в обычном API игрока, включая историю и варианты выбора.

Типы категории эффекта: gift, complication, paradox; редкости common, uncommon, rare, epic, special. Тип `narrative` означает применение через мастера, `table` — использование за столом, `choice3` — системный выбор на следующую выдачу. Для обычных собственных эффектов не подменяйте зарезервированный `parameters.standard_index`; он используется для штатных механик передачи №90/91.

Активные наборы ограничивают доступную колоду. Если наборов нет, доступны все активные глобальные и собственные эффекты. Для кампании, в которой нужны только собственные копии, создайте набор с ними: простое создание копии не исключает оригинал. Вес из активных наборов заменяет индивидуальный вес для включённых карточек; записи с нулевым весом исключаются. Отдельно нормализуются веса категорий.

В «Обзор» подтверждайте описание применения, не создавая фактов мира автоматически. Отклонённый эффект снова активен. Квест можно вернуть на доработку; повторное подтверждение не выдаёт вторую награду. Ручная дополнительная выдача эффекта не отменяет старую карточку — при необходимости сначала отмените её отдельно.

### Передача и обмен

Игрок использует №90 или №91, указывает ID предлагаемого эффекта и персонажа получателя. ID виден в списке своих карточек. Для обмена нужно также указать ID карточки получателя (согласуйте это с ним за столом). Система запрашивает его согласие; после согласия мастер проверяет применимость. Только одобрение меняет текущего владельца карточек. Отклонение возвращает заблокированные карточки в active. Первоначальная выдача остаётся записанной в issued_to, поэтому передача не открывает бесплатный повторный розыгрыш.

### Кошельки и казино

Жетоны изолированы по паре user/campaign. Стартовый баланс выдаётся при первом создании кошелька и фиксируется отдельной ledger-записью. Изменение initial_balance не пополняет существующие кошельки повторно.

Корректировки требуют причины; отрицательные значения списывают, но не могут создать отрицательный баланс. Каждая корректировка видна пользователю и в аудите. Для полного сброса используйте корректировки с общей понятной причиной; массовой кнопки reset в этой версии нет.

Параметры игр: включение, min/max, правила выплат и допустимые веса. При сохранении сервер проверяет JSON и повышает версию. Существующий раунд всегда завершается по сохранённой конфигурации. Честные монета, 2d6, рулетка и колоды не изменяют вероятности для отдельных пользователей. Lucky Wheel и Slots используют опубликованные веса. Таблица math пересчитывается на сервере.

Для баланса используйте полную выплату и чистую прибыль правильно: ставка 10, gross multiplier 1.9 → списание 10, начисление 19, чистый результат +9 ST. При удвоении Blackjack суммарная ставка возрастает. Денежных операций, платежей и внешней конвертации нет.

## Системный администратор

```bash
docker compose exec backend python manage.py createsuperuser
docker compose exec backend python manage.py seed_initial_data
docker compose exec backend python manage.py spectacular --file openapi.yaml --validate --fail-on-warn
```

Откройте `/admin/`. Системная админка предназначена для доверенного оператора. Обычные мастера работают в React. Исторические раунды, кошельки, ledger, заявки, награды и аудит в Admin доступны только для чтения. Не редактируйте финансовые данные SQL-командами: это обходит ledger и сервисные гарантии.

Для глобальной библиотечной правки используйте Django Admin; повторный seed обновляет стандартные записи со стабильными codes и может восстановить исходные тексты. Локальные custom/import-записи не затрагиваются. Поэтому изменённый стандартный эффект, который нужно сохранить независимо от будущих seed, копируйте в контент кампании.

## Production checklist запуска

1. Установите собственный секрет Django и пароль PostgreSQL. Не используйте значения из примера для публичного сервера. Храните `.env` вне git и архива исходников.
2. Настройте домен и сертификат. При прямом TLS в Nginx добавьте `listen 443 ssl`, ssl_certificate/ssl_certificate_key и redirect 80→443; сертификаты монтируйте read-only и продлевайте внешним ACME-клиентом.
3. В `.env`: `DJANGO_DEBUG=0`, `COOKIE_SECURE=1`, `DJANGO_ALLOWED_HOSTS=your.domain`, `CSRF_TRUSTED_ORIGINS=https://your.domain`. Включите localhost в allowed hosts, если используете показанный внутренний healthcheck, либо настройте его Host отдельно.
4. Если TLS завершается на другом reverse proxy, разрешайте доступ к Nginx только от него, правильно передавайте X-Forwarded-Proto. Текущий nginx.conf использует `$scheme`; при внешнем TLS-терминаторе настройте доверенный forwarding, не принимайте этот заголовок от произвольных клиентов. Backend порт в базовом Compose наружу не публикуется.
5. Поднимите db, выполните migrate, seed_initial_data, collectstatic, создайте администратора, затем запустите backend/web. Все запросы SPA/API/Admin идут на одном origin.
6. Выполните CI/тесты на настоящем PostgreSQL и приёмку двух пользователей до публичного запуска. Не включайте TEST_SQLITE в production. Проверка concurrency автоматически пропускается на SQLite и не доказывает корректность блокировок там.
7. Проверьте резервное копирование/восстановление и журнал ошибок. Настройка TLS, внешнего DNS, мониторинга и реального сервера требует выбранного окружения; эти действия не выполнялись в рабочей среде сборки.

Раздаваемый nginx.conf — рабочая конфигурация локального HTTP на 8080. Это не утверждение о готовом HTTPS-развёртывании в интернете.

## Резервные копии

```bash
# В shell на сервере; файлы резервных копий храните защищённо.
docker compose exec -T db pg_dump -U sessionlab -d sessionlab -Fc > sessionlab.dump
# Восстановление в подготовленную пустую БД:
docker compose exec -T db pg_restore -U sessionlab -d sessionlab --no-owner < sessionlab.dump
```

Используйте своё имя БД/пользователя. Не запускайте restore поверх рабочей БД без отдельного плана. Секрет Django и настройки окружения храните отдельно от дампа. User uploads в этой версии отсутствуют, аватары задаются URL.

## Надёжность и ограничения эксплуатации

Все игровые мутации блокируют строку кампании внутри `transaction.atomic`. Это даёт единый порядок операций, исключает гонки между лимитами/наградами/кошельками и убирает циклический порядок блокировок. Кошелёк дополнительно блокируется `select_for_update`; PostgreSQL constraint запрещает отрицательный баланс. Ошибка приводит к откату раунда, ledger и idempotency record вместе.

Удобная для небольшой D&D-группы сериализация может стать узким местом у больших кампаний. Прежде чем менять её на более узкие locks, добавьте нагрузочные и конкурентные проверки для всего порядка блокировок. Несколько кампаний не блокируют друг друга.

Idempotency records не очищаются автоматически. Ledger/round/audit не удаляются через UI. Настройте политику хранения и бэкапы при длительной эксплуатации; не удаляйте ключи, пока возможен повтор соответствующего критического запроса.

Django-axes хранит ошибки входа в БД и блокирует комбинацию username/IP после пяти неудач на час. В штатном проксировании backend видит адрес прокси; проверьте конфигурацию доверенного IP, если нужна более точная сегментация. Общий DRF throttling в этой версии использует локальный cache процесса и не заменяет общий rate limit на Nginx/балансировщике при нескольких worker.

Пароли хешируются штатным Django PBKDF2; клиент не хранит session token в localStorage. Theme/reduced-motion и выбранные ID — пользовательские UI-настройки. Ключи неоднозначно завершившихся запросов временно сохраняются в sessionStorage и удаляются при успехе/выходе.

Для разработки можно использовать `npm run dev` из корня после установки зависимостей в frontend и Python в `.venv`; runner загрузит локальный `.env` и запустит Django+Vite. Не используйте dev runner как production-сервер. Опция `SESSIONLAB_SMOKE=1` запускает локальный HTTP smoke-тест и создаёт случайный QA-аккаунт только в одноразовой БД; по умолчанию она выключена.

## Локальная версия без Docker

Основной Windows CMD сценарий с SQLite и двумя консолями находится в README. Переменные локального запуска лежат в `.env.local`. Команды администратора выполняются через `.venv\Scripts\python.exe backend\manage.py createsuperuser` и `.venv\Scripts\python.exe backend\manage.py seed_initial_data` из корня. Перед обновлением остановите backend и скопируйте файл `backend/development.sqlite3` в безопасное место. Не заменяйте пользовательскую БД содержимым исходного архива.

Инструкции по новым ролям, комнате, листам, магии и инициативе: `docs/ROOMS_AND_SHEETS.md`. Новые таблицы добавляют миграции 0004/0005; существующие кампании, персонажи и библиотека сохраняются.

## Живые обновления

Сервер использует SSE с session cookies; Redis не нужен. Для локального `runserver` оставьте потоки включёнными (не используйте --nothreading). Production Gunicorn запускается с `--worker-class gthread --threads 16 --workers 3`; каждый поток SSE занимает один поток worker. Nginx отключает proxy_buffering для `/api/` и использует read timeout 60s. Заранее планируйте запас потоков для обычного API. Эта конфигурация не проходила нагрузочную приёмку.

Браузер перечитывает данные при ревизии и имеет fallback 5 секунд. Мастерские изменения через React создают аудит; прямые SQL/Admin-изменения не являются поддержанным источником live-уведомлений. Ревизии не несут текста/результатов, все данные выдаются через проверяющий права REST.

SQLite в локальном режиме использует `transaction_mode=IMMEDIATE`, timeout 20s. Это предотвращает типичные конфликты перехода от чтения к записи в наших коротких транзакциях, но сериализует записи всей базы. Не используйте локальную SQLite как замену проверке PostgreSQL-блокировок в CI.
