## Backend

Проверяются реальные Django ORM-модели и DRF endpoints, а не подставленный frontend-контент:

- Регистрация, вход/выход, текущий пользователь, обязательный CSRF даже для анонимной регистрации.
- Создание кампании, вступление по коду, персонаж, изоляция чужой кампании/персонажа/кошелька и запрет DM-операций игроку.
- Стабильность выдачи, лимит, идемпотентный ответ, конфликт ключа при изменённом body.
- Снимки текста и удаление secret из библиотеки, истории и choices; история не меняется при редактировании определения.
- Применение эффекта, отклонение мастером, истечение сессии, перенос права на выбор из трёх, запрет повторного choice3.
- Передача/обмен с согласием и одобрением; исходный лимит выдачи не обнуляется после смены владельца карточки.
- Однократное начисление квестовой награды, повторный запрос, запрет игроку подтверждать без прав.
- Стартовый грант один раз, отклонение ставки без баланса, DB constraint на неотрицательный баланс.
- Откат раунда/ledger/баланса при искусственно вызванной ошибке в середине операции.
- Каждый из 7 режимов создаётся и завершается на сервере; баланс равен initial − stakes + payouts.
- Blackjack скрывает закрытую карту/колоду, корректно удваивает суммарную ставку. Повторное завершение отклоняется.
- Сохранение версии правил в истории, изоляция редактирования контента и запрет изменения глобальной библиотеки мастером.
- Идемпотентность импорта, scope наборов, отклонение некорректного JSON-формата ставок.
- Новые листы: ограничения характеристик/формул, принадлежность персонажа, приватные записи, публичная party-проекция, конфликт версий.
- Броски и магия: серверная математика d20 и кубиков, критическое удвоение только кубиков, дополнительные лучи, рост заговоров, усиление ячейкой, транзакционный откат при ошибке, однократное списание при повторе.
- Инициатива: один бросок игрока, скрытый NPC, доступ мастера, устаревшая версия, пауза/продолжение, проверка ID. SSE: ревизия, доступ активного участника и отзыв доступа.

Математика тестируется отдельно: все числа/внешние ставки рулетки, все 36 пар 2d6, тузы/soft scores/natural blackjack/push/bust, 50/50 монеты, комбинаторный RTP слотов, фактические 51 оставшаяся карта Higher or Lower, веса Lucky Wheel, границы взвешенного выбора и широкий статистический sanity check на 20000 выборов.

Два дополнительных конкурентных теста включаются только на PostgreSQL:

1. Два параллельных запроса не расходуют одни и те же последние жетоны.
2. Два параллельных запроса с одним Idempotency-Key создают один раунд и одно списание.

Они присутствуют в CI, но **не запускались на настоящем PostgreSQL в этой среде**. Пропуск этих тестов нельзя считать доказательством корректности PostgreSQL-развёртывания.

## Frontend

Тесты включают монтирование App с React Router и TanStack Query, контролируемый HTTP transport и отдельные UI-компоненты:

- Dashboard получает кампанию, персонажа, баланс.
- Отказ сессии показывает форму входа.
- Навигация к эффектам работает.
- Разные маршруты/меню игрока и мастера, переключение вида и редирект игрока с мастерского URL.
- Тема/reduced-motion сохраняются запросом к профилю.
- Сохранённый активный Blackjack восстанавливает доступные действия после нового монтирования.
- Регистрация/логин переключаются, поля и ограничения формы видимы.
- Pending-кнопки заблокированы, диалог имеет доступное имя и закрывается Escape, пагинация работает.
- Ошибки API доступны для чтения и повторного запроса.
- CSRF и cookies отправляются; после неоднозначной сетевой ошибки повтор использует тот же ключ.
- Blackjack не дорисовывает данные закрытой карты, рулетка имеет европейские сектора и указатель, кости показывают значения ответа.
- Редактирование листа создаёт черновик и блокирует броски до сохранения.
- SSE invalidates только нужную кампанию, не удваивает одинаковые ревизии, очищает данные при отзыве доступа, переходит на fallback и останавливает его после восстановления.

Эти тесты используют fixtures только внутри test-файлов. Production-контент всегда загружается с Django API.

## Что здесь не подтверждено

- Сборка и запуск Docker-образов, Nginx/Gunicorn/PostgreSQL в Compose.
- PostgreSQL row-level locking и многопроцессная нагрузка.
- Полный авторизованный браузерный сценарий, визуальная приёмка Dashboard/DM/семи игр в реальном браузере, замеры плавности и мобильная приёмка.
- HTTPS, cookies на реальном домене, DNS, мониторинг, резервное восстановление в production.
- Длительный D&D playtest и игровой баланс Homebrew для обеих редакций.

Повторная проверка: healthcheck вынесен в `/api/health/` без пользовательского throttling. Проверены 105 последовательных запросов без расходования квоты авторизации и ответ 503 без раскрытия деталей при недоступной БД. HTTP smoke проверяется отдельно от браузерной приёмки; прямой вызов Django не подтверждает работу reverse proxy или CSS на реальном мобильном браузере.

## Повторить проверки

С настоящим PostgreSQL:

```bash
cd backend
python -m pytest -q
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py spectacular --file openapi.yaml --validate --fail-on-warn
```

Frontend:

```bash
cd frontend
npm ci
npm test
npm run build
```

Сквозные HTTP тесты включены как `scripts/smoke_http.py` и `scripts/smoke_room_http.py`. Первый использует настоящие CSRF/session endpoints, создаёт случайного QA-пользователя в **одноразовой локальной БД**, выполняет регистрацию, кампанию/персонажа/сессию, повтор эффекта, подтверждение квеста, все игры, проверку статистики/истечения и выход. Запускать только на подготовленной локальной тестовой среде:

```bash
python scripts/smoke_http.py http://localhost:5173
python scripts/smoke_room_http.py http://localhost:5173
```

Для браузерной приёмки: два отдельных аккаунта (dm/player), первая кампания и персонажи, новая активная сессия; получить эффект и перезагрузить; запросить сюжетное применение; подтвердить/отклонить в другом окне; выдать квест и подтвердить награду; сыграть семь режимов; прервать/возобновить карточный раунд; сменить тему/reduced motion; повторить на ширинах 375/768/1440. В network панели проверить отсутствие secret/deck/закрытой карты и отсутствие повторных списаний при повторе ключа. Затем выполнить оба PostgreSQL concurrency теста и Compose startup.

HTTP smoke повторно выполнен против Django на 127.0.0.1:8765 в отдельной временной SQLite-БД после migrate и двух запусков seed. База удалена после проверки. Vite/Nginx не участвовали в этом прогоне.


Новый `smoke_room_http.py` запущен вместе со старым smoke через настоящие HTTP endpoint Django на 127.0.0.1:8765 в отдельной временной SQLite-БД после migrate и seed. Три аккаунта проверяют авторизацию/изоляцию, SSE доставляет ревизию другой сессии, два параллельных клиента с одним ключом применения заклинания получают один ответ и расходуют одну ячейку. Проверены скрытый бросок, скрытый NPC и общий HP. Это узкий конкурентный сценарий SQLite, не доказательство производственной нагрузки PostgreSQL.

Последняя сборка TypeScript/Vite успешна. 25 тестов React прошли, включая однокнопочное применение сохранённого заклинания с тремя отдельными результатами. `makemigrations --check --dry-run`, `manage.py check` и OpenAPI `--validate --fail-on-warn` проверены после изменений схемы.
